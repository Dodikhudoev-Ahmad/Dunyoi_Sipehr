## Stage 5 — Backend Audit & Bug Fixes — DONE (2026-08-17)

Full audit of `backend/` against `docs/MASTER_TZ.md` and `docs/DECISIONS.md` (frontend explicitly out of scope for this pass). Found and fixed:

1. **Refresh cookie never persisted in default local dev** (`Api/Controllers/AuthController.cs`). `SetRefreshCookie` set `Secure = true` unconditionally; the dev frontend talks to the API over plain `http://localhost:5091` by default, and browsers silently drop `Secure` cookies on a non-HTTPS origin. Login "worked" (access token returned) but the refresh cookie never saved, so sessions died with the 15-minute access token and silent-refresh could never fire. Fixed: `Secure` is now `env.IsProduction() || Request.IsHttps` — still `true` whenever the request is actually served over HTTPS (including a dev run behind HTTPS), `false` only on plain-http dev. No dev-flow/README change needed since this is transparent to how `dotnet run`/Vite are started.

2. **Migrations never applied in Production** (`Api/Program.cs`). `db.Database.MigrateAsync()` only ran inside `DevSeeder.SeedAsync`, itself gated to `Development`. A first Railway deploy would boot against a schema-less database. Fixed: migrations now run unconditionally at startup, before the dev-only seeder, in every environment — see `docs/DECISIONS.md` DEC-008 for the reasoning (migrate-on-boot vs. a separate deploy step) and the tradeoff it accepts.

3. **Admin list endpoints had no sorting/filtering, contradicting MASTER_TZ §5** ("Pagination/filtering/sorting on all admin list endpoints with an explicit sortable-fields whitelist"). Every `ListAdmin*Query` handler (Destinations, Offers, Services, Cities, Countries, Testimonials, FAQ, TravelRequests, SiteContent, AuditLog) only supported pagination. Fixed: added a shared `ApplySort` extension (`Application/Common/Models/QuerySortExtensions.cs`) that resolves `sortBy`/`sortDir` against a per-entity `SortWhitelist` dictionary of key-selector expressions — an unrecognized `sortBy` silently falls back to the entity's default sort rather than building `OrderBy` from raw client input. Added `sortBy`/`sortDir` query params plus baseline filters (`isPublished`, `search`, entity-appropriate extras) to all ten admin list controllers/queries.

4. **`Editor` vs `SuperAdmin` role had no effect anywhere** — every admin endpoint used a bare `[Authorize]`. Fixed: gated the destructive `DELETE` endpoint on every admin CMS controller to `SuperAdmin` via `[Authorize(Roles = nameof(AdminRole.SuperAdmin))]` (the JWT already carries the role as a standard claim). See DEC-009 — deletion is the one irreversible admin action, and there's currently no admin-user-management feature to provision `Editor` accounts, so this is a scoped, defensible use of the existing role field rather than a new authorization surface.

5. **`Destination.CityId` FK defaulted to cascade delete**, unlike the equivalent `Country → City` relationship which is explicitly `Restrict` (`Infrastructure/Persistence/Configurations/GeoConfigurations.cs`). `DeleteCityCommandHandler` already blocks deleting a City with existing Destinations at the application layer, but the database itself would have silently cascade-deleted real published Destinations if that guard were ever bypassed (race, future tooling, direct SQL). Fixed: `DestinationConfiguration` now explicitly sets `OnDelete(DeleteBehavior.Restrict)` on `Destination.City`, matching Country → City. New migration `FixDestinationCityRestrictAndOfferDestinationIndex`.

6. **`OfferCommands` (`Create`/`Update`) never validated `DestinationId`/`ServiceIds` before insert**, unlike every other admin command (City validates `CountryId`, Destination validates slug uniqueness, etc.). A stale or malformed reference (e.g. a Service deleted moments earlier) would throw an unhandled `DbUpdateException` (FK violation) at `SaveChangesAsync`, surfacing as a generic 500 instead of a `VALIDATION_FAILED` `Result`. Fixed: both handlers now check the referenced Destination/Services exist first and return `Error.Validation(...)` if not.

Reviewed and found already correct, no change needed: rate limiting (MASTER_TZ §5 only requires it on login + Travel Request submission — both covered, no other public write endpoints exist); CORS (dev wildcard is intentionally scoped to `localhost`/`127.0.0.1`, Production is strictly `Cors:AllowedOrigins`-driven); public query handlers all filter `IsPublished` and follow the `ru`-fallback locale rule correctly; TravelRequest state machine transitions.

## Stage 7 — Combined Frontend+Backend Live Audit — DONE (2026-08-17)

Triggered by a user-reported crash: opening any admin Destination edit form rendered a blank white screen. Root-caused (`d.highlights` — a field that doesn't exist on the real `UpsertDestinationInput` DTO, only inside `d.translations[]`) and fixed, per the report. But Stage 5/6 had each audited backend and frontend by reading code, never by running both together and clicking real pages — so this stage's mandate was to actually run `dotnet run` + `npm run dev` against a live Postgres, log in as a real admin, and drive every admin edit form with Playwright (headless Chromium), reading the real JSON off the wire instead of trusting hand-written TypeScript types. That method surfaced two systemic bugs the two prior code-reading audits both missed entirely — one frontend, one backend.

**1. Reported bug, fixed as asked.** `DestinationFormPage.tsx` line ~90: `t?.highlights ?? (l === 'ru' ? d.highlights : [])`. `d` (the response of `GET /admin/destinations/{id}`) is an `UpsertDestinationInput` — confirmed against the C# DTO and live JSON — which has no top-level `title`/`summary`/`description`/`highlights`, only `translations[]`. `.join('\n')` on the resulting `undefined` threw, React unmounted with no error boundary, page went blank. Fixed per the chosen option (removed the fabricated top-level fallback entirely — `t?.highlights ?? []` for every locale — since there is no such thing as "the ru version" outside the translations array; see inline comment).

**2. The same bug crashed on literally every destination, not just some — because of a deeper, previously-unknown frontend bug.** Reproduced live and confirmed via `curl`: the backend serializes the `Locale` enum using the raw C# member name (`"Ru"`/`"Tg"`/`"En"`), not the app's lowercase codes (`'ru'`/`'tg'`/`'en'`) that `LOCALES`/routing/i18n use everywhere. Every admin form's `translations?.find((t) => t.locale === l)` therefore *never* matched, on any record — `t` was always `undefined`. For Destination that forced the crash path above on every load; for every other entity (Offer, Service, Testimonial, FAQ, SiteContent, Country, City) it silently rendered **blank translation fields for an existing record**, a real data-loss risk (an admin re-saving what looked like an empty field would wipe real content). Fixed with one shared, tested helper — `src/lib/translations.ts` (`findTranslation`, case-insensitive comparison) — used everywhere the old broken pattern was, confirmed by grep to have zero remaining occurrences.

**3. Field-by-field DTO audit (per the ask) found the frontend's hand-written types were wrong almost everywhere, not just for Destination.** Every `api/*.ts` admin `adminGet`/`adminList` method was typed against the bloated public-facing type (`Destination`, `Offer`, `Service`, etc. — which carries flattened `title`/`name`/`quote`/etc.), when the actual admin DTOs (`UpsertDestinationInput`, `UpsertOfferInput`, `AdminServiceDto`, `AdminCityDto`, `AdminCountryDto`, `AdminFaqItemDto`, `AdminSiteContentDto` — `AdminTestimonialDto` is the one exception, since `AuthorName`/`AuthorCountry`/`Rating` genuinely aren't translated) never carry those flattened fields. Added precise `Admin*Item`/`Admin*Detail`/`Admin*ListItem` types mirroring each DTO exactly and rewired every `api/*.ts` module and every list/form page onto them — which is what caught (via `tsc`, then confirmed live): the admin Destinations *list* page rendering a blank "Название" column (DTO has no `Title`, only `CityName` — swapped the column); the Offer form's Destination-picker and Service-picker dropdowns rendering blank option labels for the same reason (fixed using `slug`/`cityName` and `findTranslation(...).name` respectively); `Offer.currency`, sent by the backend as `"Usd"` not `"USD"`, never matching the `<Select>`'s uppercase `<option>` values so the currency dropdown silently showed nothing selected on an existing offer (fixed by normalizing on load — confirmed live that saving `"USD"` round-trips fine, so only the display side needed a fix); and `authApi.bootstrap` was typed to return login tokens it never actually sends (already fixed in Stage 6, re-confirmed here).

**4. Separate, severe backend bug, found only because live testing did a real save-after-fetch (not a same-session Create+Update): every admin "Update" operation on every translatable entity was broken.** `UpdateOfferCommandHandler` (and the identical pattern in Destination/Service/Testimonial/Faq/SiteContent/City/Country) fetched the entity with `db.Offers.FirstOrDefaultAsync(...)` — no `.Include(o => o.Translations)`. `SetTranslation` then searched an unloaded (so empty) in-memory collection, never found the already-persisted row, and `Add()`-ed a duplicate — which collides with the composite primary key `(EntityId, Locale)` on save. Reproduced live: `PUT /admin/offers/{id}` 500'd with `duplicate key value violates unique constraint "PK_OfferTranslation"` against a real Postgres instance. The existing 42-test xUnit suite never caught this because none of its tests reload an entity through a *fresh* `DbContext` after creating it — the tracked-in-memory `Translations` collection from the `Create` call masked the missing `.Include()`. Fixed by adding `.Include(x => x.Translations)` (plus `.Include(o => o.OfferServices)` for Offer, which has the same problem via `SetServices`) to all 8 `Update*CommandHandler`s. Added a regression test (`DestinationCrudTests.Update_ExistingTranslations_UpdatesInPlace_DoesNotThrowOnDuplicateLocale`) that deliberately reloads through a second `DbContext` instance against the same in-memory database to actually exercise this — verified it fails without the fix (same duplicate-key exception, reproduced by temporarily reverting the `.Include()` and re-running) and passes with it.

**5. Added a React error boundary around the whole admin route tree** (`AdminErrorBoundary` in `src/admin/components/ErrorBoundary.tsx`, wrapping `<Routes>` in `AdminApp.tsx`, keyed by pathname so client-side navigation after a crash actually recovers). Verified live by temporarily throwing inside `DestinationFormPage` and confirming the boundary shows a "Что-то пошло не так" screen with Back/Dashboard buttons instead of a blank page — this is a safety net for the *next* bug of this class, not a substitute for the DTO fixes above.

**6. `docs/API_CONTRACT.md` vs. actual controller routes: no endpoint mismatches.** Every route in every controller (`backend/Api/Controllers/**`) matches something documented, and nothing documented is unimplemented — grepped every `[Route]`/`[Http*]` attribute across all 15 controllers against the contract line by line. ### Frontend
